# Testing

This document defines how Arcade behavior is inventoried for testing and how test cases are derived from that inventory. It exists so coverage is driven by the behavior Arcade specifies rather than by bug history: when a feature is added or changed, this document says what test cases it owes and where they belong.

**This document is binding.** The behavior inventory, the required cases rule, and the evidence rules are obligations on the suite, not descriptions of it. That is why it lives here rather than under `docs/`: everything in `docs/` describes how Arcade works and carries no obligation, while this file states what a change must do before it is finished. Where the suite and this document disagree, the suite is wrong.

The companion manifest `__tests__/COVERAGE.md` maps every inventory entry below to the tests that exercise it. It is evidence, not definition: this document says what is owed, the manifest records what has been paid. A change that alters behavior updates the inventory here, the manifest, and the tests together.

[e2e-eval.md](../docs/e2e-eval.md) describes the three test layers Arcade runs — focused unit tests, the always-on context-propagation suite, and the opt-in real-provider evals. This document governs the first two. The third is evidence of behavioral fidelity, not of the deterministic contract, so it never satisfies an inventory entry on its own; see "Evidence Rules" below.

## Coverage Model

Four documents under `docs/` describe the behavior this inventory decomposes: [arcade.md](../docs/arcade.md) gives the mental model and mechanisms, [service-apis.md](../docs/service-apis.md) the connector-, host-, and worker-facing contracts, [configuration.md](../docs/configuration.md) the deployment schema, and [observability.md](../docs/observability.md) the three observability surfaces. They are descriptive; the **behavior entries** below — individually testable rules, each with a stable id — are what the suite is held to. An entry is the unit of coverage accounting: the manifest marks it covered, partially covered, or uncovered, naming the tests that prove it.

An entry and the description it came from should agree. When they do not, one of them is wrong and the same change fixes both; an entry does not silently redefine behavior, and a description does not excuse a missing test.

A behavior entry is not one test. Most entries expand into several required cases along two axes, and defects concentrate at the intersections.

### Contexts

One rule keeps one meaning across the system, but each admission is a separate execution path. The contexts are:

- **stage** — trigger or action,
- **backend** — `claude-sdk`, `claude-sdk-tst`, `openai-sdk`, `openai-sdk-tst`, `pi-agent`, or `in-process`,
- **entry** — fresh activation, targeted continuation, deflected re-entry, or a jump/rewind continuation,
- **store** — in-memory, JSON-file, and a fresh service reading persisted state after a restart,
- **connector** — MCP or Web App,
- **audience** — originator, `permissionApprover`, or another named audience.

Each rule states which contexts it spans. A rule's entry owes cases in every context it spans, and a rejection case in at least one context that excludes it.

### Outcomes

Every case exercises the rule to a definite outcome. The outcome families are:

- **accepted** — the happy path; the work is admitted and runs to completion,
- **idle** — nothing matched, and no run or durable state is created,
- **handshake-required** — activation is gated on a workspace, run-choice, or arc-choice answer,
- **rejected** — a routing or authorization invariant refused the input,
- **failed** — required trigger work failed and admission closes with its reason,
- **parks and resumes** — a recoverable backend failure holds the run in durable execution-control state and a later resume carries it forward,
- **deflects** — the arc leaves its own scope and the run suspends,
- **poisons** — the traversal terminates under a named reason code, or a routine persists as failed.

### Required cases rule

For every behavior entry:

1. One accepted case per context the rule spans.
2. For a rule the routing layer fans out across backends, one case per routed backend.
3. For a rule with durable effect, one case proving the state survives onto a fresh service reading the persisted store.
4. For a rule that admits recoverable failure, one parked case and one resumed case, plus the exhaustion case its retry policy defines.
5. For a connector-facing rule, one rejection case per authorization or validation invariant.
6. For a rule whose spec names distinct reason codes or outcome values, one case per named value.

Cases 2–6 may live in one test when the scenario naturally covers them, but the manifest must name which entry cases a test proves.

### Evidence Rules

The manifest accepts deterministic tests from the root and web packages' `unit` Vitest projects as evidence. Each package owns its test runner and dependencies; ARM runs both packages' test scripts. Two consequences follow:

- A live eval under `eval/` never moves an entry to **covered** on its own. An entry whose only evidence is an eval is **partial**, and the Missing column says so. This keeps eval-only coverage visible instead of reading as proven.
- Every test name cited in the manifest must be globally unique across the suite, so that grepping the name locates exactly one test. A behavior tested once per backend is named per backend rather than repeated verbatim.

This inventory covers the tests under `__tests__/` and `web/__tests__/`. Tests under `benchmarks/`, `e2e-test/`, and `examples/` are outside it and never serve as evidence for an entry.

### Test Files

Test files are organized by behavior area, one area per file where the area is large enough to fill one. This is what makes the inventory navigable without tooling: an entry's id names the file its tests belong in, so a missing case and a misplaced test are both visible on inspection.

An area whose tests are few may share a file with a related area, and a large area may split across several, but a file that serves many unrelated areas has outgrown its name and should be split.

### Harness and Imports

A test that exercises one module imports that module directly. A test that assembles two or more services imports through `src/testing.ts`.

The split follows from what each import means. A unit test naming `src/service/token-usage.js` states which module it covers, and reaching for the curated surface instead would hide that. A test that stands up an Arc host and the hub together is exercising the same composition an embedder does, so it should be held to the same surface an embedder gets — and anything it needs that the surface lacks is a gap in the surface, not a reason to reach past it. Assembling through the `makeWorkerHub` and `makeArcHostWithSource` helpers counts as assembling services.

Shared setup lives in one of five harnesses, and a helper used by more than one file belongs in the narrowest one that covers its callers:

- `__tests__/helpers.ts` — cross-cutting fixtures and service assembly.
- `__tests__/replay-helpers.ts` — the replay area.
- `__tests__/backend-helpers.ts` — backend routines, tasks, and SDK doubles.
- `__tests__/arc-host-helpers.ts` — Arc host step drivers, activation, and dialog projection.
- `__tests__/worker-hub-helpers.ts` — hub submission, lifecycle channels, and SDK message streams.

Folding two copies of a helper into one is only safe when the copies were behaviorally identical. Where they differ, keep them separate or make the difference an argument; never let a merge quietly change what a test asserts.

## Adding or Changing a Feature

1. Write or update the owning description under `docs/` first, so the behavior is stated before it is inventoried.
2. Add or update behavior entries below, one per new rule, keeping ids stable.
3. Expand each entry with the required cases rule and write the tests.
4. Update `__tests__/COVERAGE.md` in the same change.

A change is not finished until steps 2 through 4 are done. Adding behavior without an entry, or an entry without evidence, leaves the suite in a state this document forbids.

When a test must change during a semantic change, first decide whether the old expectation exposed a real bug. Do not weaken a test to match implementation behavior unless the behavior intentionally changed.

## Behavior Inventory

Ids are `area.slug`. The **Behavior** column states the rule and any entry-specific required cases beyond the standard rubric.

Descendant traversal is temporarily disabled, whether or not the supplied root is itself a workspace. Nested workspaces and roots inside generated output trees are discoverable when explicitly supplied. Results are deduplicated and empty when no supplied root matches. |
| `disc.bundle-load` | Each immediate subdirectory of an Arc directory is one bundle whose name becomes the source name, and it must contain exactly one `*.arc.js` file. A missing Arc directory loads zero bundles; a subdirectory without an Arc source is an error. |
| `disc.manifest` | An optional `arcade.json` configures workspace scope, the `"role"`-by-default `contextIsolation` floor, and the longest-prefix bundle map, whose values resolve relative to the manifest directory unless absolute. Context isolation accepts only `"role"` or `"node"`. A malformed manifest and a bundle path that does not resolve to an existing directory are both errors. |
| `disc.upsert` | Reloading one discovered Arc source replaces its latest registered document and leaves unrelated bundles untouched. Existing runs remain pinned to the immutable snapshot they started with. |
| `disc.workspace-binding` | Arcs discovered from a connector working root carry that workspace path into fresh activation. Arcs registered from the startup directory stay workspace-less and take a workspace handshake when their policy requires one. |
| `reg.roots` | Registration registers every root Arc in a document, persists the source, and logs the registration. | `reg.worker-role-metadata` | Registration validates every node-level `hostParams.workerRole` as a non-empty string and `hostParams.tools` as an array of strings, and rejects a document whose instruction `hostParams` declare a `workerRole`, including nested inside branches and invoke bodies. An instruction may still carry its own `tools`. The checks run before any registration side effect, so a rejected source registers cleanly once fixed. |
| `reg.context-isolation` | Registration accepts absent, `"role"`, or `"node"` node-level `hostParams.contextIsolation`, rejects malformed node values with source and node identifiers, and rejects statement-level declarations. The statement walk traverses `if`, label, invoke, and `$map` bodies, including compound statements nested inside a map. |
| `reg.host-module` | Each host module registration owns one exact validated declaration and its implementation. A second registration throws. Adding or removing a module validates every current document and commits atomically. Each referenced operation requires a submit implementation; variable-only modules such as audience require none. |
| `reg.known-roles` | The host reports the set of worker roles referenced by registered Arc documents, including the default worker role. |

### Arc Runs (`run`)

| Id | Behavior |
| --- | --- |
| `run.activation` | An untargeted inbound evaluates registered Arc triggers and returns the activation fork; no match returns an empty worklist (idle), and neither a missing run nor an unmatched trigger creates durable state. A matched arc returns an `action` step carrying its frontier. |
| `run.workspace-resolution` | A run-scoped activation resolves its workspace under the artifact root keyed by run id; an arc-scoped activation uses the registered or discovered workspace. The resolved path persists on the run state and is what backends receive. |
| `run.fan-out` | The activation policy governs the fan-out and survives a semantic-trigger round-trip on the live session rather than regressing to `first`. Each step carries at most one run identity — plurality lives only in the array — so a mixed fan-out yields an `action` step with an `arcRunId` and a `handshake` step with its preparation `arcRunId`, `handshakeId`, and `arcRef`. Policy `first` applies by probe order, not by match settlement order. |
| `run.trigger-probe` | Trigger work stays out of durable run state until activation. A fresh semantic probe pins the documents current when probing began, an unresolved probe expires without later activating, failed semantic trigger work retires only its probe, preserves pre-existing deflected executions, and finalizes successful sibling matches once all probes settle. A concurrently settled activation batch finalizes exactly once. |
| `run.deps-snapshot` | An activated run persists its dependency set and snapshot id alongside its state. The snapshot holds every document the run depends on, imports included, plus the exact declarations of the host modules imported by those documents. Runtime reconstruction requires structurally identical current declarations before traversal progress or host invocation and does not revalidate persisted pins. |
| `run.targeted-reentry` | A targeted `arcRunId` re-enters that run from its persisted action state without repeating its trigger, including a run whose in-memory host session was abandoned. A fresh service reconstructs disposable live state from the durable JSON snapshot and re-yields any unacknowledged instruction frontier rather than advancing it. Targeted begin checks persisted lifecycle inside action serialization, before replacing cached execution or starting the runtime. Completed, deflected, and poisoned executions return an empty worklist, preserving traversal, replay, deadlines, events, frontier identity, and cached failure, including after reconstruction and when begin queues behind final settlement. Persisted-run fallback from trigger advancement uses the same entry guard. Interrupted active traversal remains eligible; deflected re-entry uses trigger activation. |
| `run.active-join` | Selecting an active run through run-choice immediately attaches the originating client session and emits `joined` on that submission's lifecycle channel. Joining releases exactly the handshake's existing branch hold, stays off the selected run's serialized lane, calls no known-run begin, records and projects no selecting input, creates no routine, and leaves Arc state, `reactivationCount`, worker context, pending asks, execution control, and captured parked continuations unchanged. Previously joined client sessions remain joined. Paused, capacity-limited, and transport-lost runs remain readable and resume only through the existing execution-control API; trigger-stage parks remain unpublished and absent from run-choice. Lifecycle delivery failure uses the existing shared-channel teardown. |
| `run.deflected-reentry` | A deflected run re-enters against its pinned snapshot and persisted traversals under the same run id. Replay records for the next reactivation count are written before the updated traversals and count are persisted together; an interrupted re-entry leaves the previous count authoritative and its records are ignored and removed before a later re-entry retries that count. Re-entry of one run is serialized by run id, so concurrent resolutions yield one success. |
| `run.pinned-vs-latest` | Existing runs continue on their pinned source revision while fresh runs use the latest. A pinned-only match offers no fresh candidate, a replacement whose trigger also matches offers both, and a replacement that matches while the pinned trigger does not starts fresh and leaves the old run deflected. |
| `run.context-isolation-policy` | Fresh activation captures the activating root's manifest isolation floor as required run state. That floor governs imported nodes, an imported source's manifest does not override it, and a node may raise `"role"` to `"node"` but cannot weaken `"node"`. Instruction and action-semantic tasks resolve effective isolation from their asserted single source node. Existing runs use captured policy and pinned node params after replacement while fresh runs use the replacement. Forks and rewinds inherit the source run's floor, while their new run ids give them fresh provider contexts. Persisted run records missing the required field are rejected. |
| `run.lifecycle-state` | The run's durable lifecycle reflects its outcome. A worker report of failure poisons the run under the report's reason code, and a deflect report suspends the root as deflected. |
| `run.views` | Run views distinguish live triggering, handshaking, and preparing from persisted actioning execution. Reads never persist preparation; execution takes precedence during re-entry. Lists deduplicate identities, filter by owner, sort preparation by ID before execution by descending update time and ID, and preserve artifact counts. Restart retains execution and drops preparation. Successful commit replaces preparation; failed activation, decline, expiry, and cross-ID selection release it. |
| `run.artifacts` | Artifact references reach the worker as structured semantic text, and the host tracks the run's unique artifact paths as briefs emit them, growing the run view's artifact count. One artifact path stays reachable across the writer and reader nodes that mention it. |
| `run.workspace-context` | The host returns the workspace path, resolved workspace bundle, and `reactivationCount` for one run. Live action sessions and persisted runs return their durable count; volatile trigger probes return zero. |
| `run.workspace-pruning` | The host deletes abandoned run workspaces under the artifact root, reporting how many it removed. A directory is removed only when it is named exactly as a run workspace, no persisted run state claims that id, and it is empty; failing any one of the three leaves it in place. Each guard owes a kept case. |

### Handshakes (`hs`)

| Id | Behavior |
| --- | --- |
| `hs.workspace` | A packaged arc whose policy requires a workspace, activating with none registered and no joinable run for that principal, stages a workspace handshake. The answer must be an absolute path; a relative one is invalid. The handshake can surface immediately or only once semantic trigger resolution identifies the arc, and on the answer the run is created there and the path persists. Connector-discovered arcs skip it. |
| `hs.run-choice` | When the principal already has live runs of the arc being activated, the handshake lists the eligible runs and states whether a fresh candidate is available. Candidates filter to the activated arc, multiple matching runs of one arc stay separate candidates, active and deflected runs both appear, and a pending semantic activation is not offered as a candidate. Fresh is admissible only when the latest-document probe matched, and a fresh choice for a workspace-bound arc uses the registered workspace. Accepting an active candidate returns an immediate successful receipt but defers authoritative activation or branch-local rejection until queued on-lane validation. |
| `hs.arc-choice` | Under the choose activation policy each match stages an arc-choice handshake. Activating one may in turn raise its own workspace or run-choice handshake, and declining is branch-local: it leaves that arc un-activated without affecting sibling handshakes or probes. |
| `hs.resolution` | Activation requirements carry structured decision data without presentation prose. Resolution returns `ok` with the next step, `joined` with a validated active-run id for immediate joining, `missing`, or `invalid`. Invalid values are retryable and retain the same handshake, hold, correlation, and buffered siblings. Their reason is a connector diagnostic rather than user-facing copy. A correlated `missing` deletes only that worker hub correlation, releases exactly its hold, and preserves siblings; an id with no live worker hub correlation returns `missing` before the arc host is called. Connector join authority comes from consuming `joined` on the lifecycle channel retained by the client session that submitted the activation request; possession of the low-level id alone does not create a second join result. |
| `hs.volatility` | Handshakes live only in memory, are never persisted, and do not survive a process restart. A pending handshake is garbage collected after about ten minutes, opportunistically on the next store access. Expiry strands no durable state, releases only the expired branch's worker hub hold when resolved as missing, and preserves sibling decisions and already-activated outcomes. |

### Host Interface (`host`)

| Id | Behavior |
| --- | --- |
| `host.step-shapes` | `begin` returns a flat worklist of `action`, `trigger`, `handshake`, and `rejected` steps, with an empty array meaning idle. A trigger step advances through the trigger entry point and an action step through the action entry point, each returning the next steps for the same run. |
| `host.instruction-coverage` | Coverage is keyed by instruction brief id, and Arcade forwards only `"applied"` entries into Arc's itemized application report. A batch may be covered partially; uncovered instructions remain in `apply`. Semantic requests owned by an apply instruction's postcheck remain advertised in the brief but are withheld from worker tasks until application coverage is committed. Postcheck tasks then use the updated dialog; unrelated semantic requests remain dispatchable. Semantic postcheck reports commit independently and may deflect without application coverage. Before coverage, a fresh service re-yields an `apply` instruction from durable state; a restored `postcheck` frontier keeps its semantic work but dispatches no instruction task. A repeated persistent instruction stays committable after a false postcheck, and one frontier may carry instructions in mixed apply and postcheck phases with the postcheck instruction's context preserved. |
| `host.semantic-commit` | A resolved semantic report commits into the next Arc frontier, for a single observation and for a grouped observation whose fields commit together. |
| `host.host-call` | The host submits validated calls directly to the registered host module and awaits setup acknowledgments, retaining occurrence identity and module data before handoff. Public frontiers omit host-call briefs; call-only work returns a live blocked frontier. Resolutions, interruptions, and failures after successful submission enter through module emission, the hub queue, and host advancement. Immediate emission waits for frontier installation and committed activation history. Trigger delivery uses the volatile probe identity and preserves stage context. A rejected submission during activation, advancement, or reconstruction records host poison, persists the terminal action state, and returns the ordinary terminal frontier in the current API call. Repeated advancement returns that same frontier until the driver releases the execution through `releaseAction`; release retires every participating module. Trigger rejection ends its probe before activation. Replay reproduces the poison without invoking modules. Abort remains cancellation and persistence errors propagate without synthetic poison. |
| `host.transitions` | Transitions settle inline and always first: the host resolves the new position's worker role from the transition host params, rotates the settle's dialog through the caller's projector, and acknowledges with a bare proceed before any other report. A role-scoped root projects its role before the first action walk, and a later advance derives the run's current position's role before its first report. |
| `host.deflection-acknowledgement` | The arc host recognizes `ActionBrief.deflection`, persists the pending traversals before catch work, and records a bare host-origin `deflect` acknowledgement in replay. This applies during activation and continuation; transition acknowledgement retains priority. Replay verifies the explicit deflection context modulo reference identity, and reconstructing applied catch work creates no duplicate acknowledgement. |
| `host.transition-bounds` | Transition acknowledgments do not count toward the settle-step budget, so a long guard-less corridor settles in one call. A separate backstop of 256 transitions per settle poisons under `transition-limit-exceeded`, and a projector failure poisons under `dialog-projection-failed`. |
| `host.node-metadata` | Node name and description for a run's refs come from the immutable Arc snapshot that run executed, not from the latest registered document. |
| `host.default-role` | An instruction carrying no worker-role metadata routes to the default worker rather than raising an instruction issue. |
| `host.task-surfacing` | The host surfaces pending tasks without executing them; carrying them out is the caller's responsibility. |

### Submission and Messaging (`sub`)

| Id | Behavior |
| --- | --- |
| `sub.lifecycle-events` | Submission returns its lifecycle channel immediately and routes asynchronously. `activated` carries a fresh activation or deflected re-entry that scheduled Arc work, `joined` carries an immediate active-run join, `continued` carries successful completion of one validated run-targeted purpose, `handshake-required` carries the required preparation `arcRunId` and a gated activation whose follow-on events arrive on the same channel, and `rejected` carries explicit validation or activation refusal. Exact ask settlement is the only current source of `continued`. A free submission closes when all matched branches release their existing holds; a targeted answer emits one terminal `continued` or `rejected` and closes. Under `activationPolicy: "all"`, join, fresh activation, deflected re-entry, handshake, and rejection branches settle independently. Each failed trigger routine produces `{ kind: "failed", arcRunId, routineId, reason }`, using its report message as the reason. Missing workers, explicit failures, and normalized backend exceptions preserve this contract. The host retires only the owning probe. The hub emits every failed routine, releases that probe's hold, and dispatches returned sibling activation steps. Sibling probes retain their continuations and retries. Multiple failures and successes can precede normal channel closure when all holds settle. Broken worker hub invariants or lifecycle delivery failure use the existing narrow shared-channel teardown. |
| `sub.principal-required` | A new run activation requires an inbound principal; without one the submission is rejected with that reason rather than activating. |
| `sub.answer-routing` | A targeted inbound requires `arcRunId` plus a non-empty live matching hub-generated `metadata.askId`; missing, malformed, stale, wrong-run, and wrong-shape inputs emit `rejected` before the arc host or generic run routing. The worker hub validates permission payloads before synchronously removing the resolver; question answers synchronously take the resolver, append role-private history using the audience and asking role captured by the ask, then resolve the exact waiter. Append failure restores the same ask only while its routine remains live and fails operationally. Permission decisions accept exactly `allow`, `deny`, or `allow_this_run`, preserve a valid optional object `updatedInput`, write no dialog history, and never default. `outboundMessageId` is connector-local and has no inbound meaning. |
| `sub.history` | Fresh activation and deflected re-entry record their activating inbound when activation semantics commit it. Active attachment records and projects none. A question answer appends one role-private entry authored from the ask-captured logical audience and asking role regardless of omitted or forged inbound `audience`; a permission answer appends none. |
| `sub.concurrency` | Distinct Arc runs dispatch work concurrently while one run executes one lap at a time. Ask settlement and active attachment stay off the run lane; synchronous resolver removal makes exactly one concurrent valid answer succeed. Submissions are accepted even when handler execution later fails or the handler queue is full, and a lap that exhausts the driver step budget continues draining in the background. |
| `sub.handshake-receipt` | The connector-facing handshake call converts host resolution into an `ok`, `missing`, or `invalid` receipt. Fresh activation and deflected re-entry dispatch the held inbound normally. Active-run selection returns `ok`, publishes authoritative `joined` on the originating submission channel, and releases exactly its existing hold without scheduling selected-run work. Invalid is retryable; correlated missing releases one hold, while uncorrelated missing returns before the arc host. |

### Routines (`routine`)

| Id | Behavior |
| --- | --- |
| `routine.report-normalization` | A worker report belongs to exactly one of `OutcomeReport`, `SuspensionReport`, `CancellationReport`, or `ErrorReport`, using the flat `outcome`, `suspension`, `cancellation`, or `error` discriminator respectively. Completed and deflected outcomes and failed errors finish; unavailable skips; paused, capacity-limited, and transport-lost suspensions retain the underlying continuation and produce the hub-internal queued task result. Superseded cancellation ends the routine without retaining a continuation; superseded feedback is discarded even when the worker returns another category. Every variant applies deterministic `backendDetails` replacement, retention, or explicit clearing. Invalid resolved values and exceptions escaping a real worker become `backend-error`; ordinary in-process callback exceptions become `handler-error`. |
| `routine.failure-poisons` | A failed action routine advances the host with failed coverage and its error, poisoning the run without changing its earlier admission outcome. A failed trigger routine retires its probe and produces a per-routine inbound failure while sibling probes continue. In either stage the routine state and routine:failed event retain the worker error. |
